## 4. Image strategy — flagged for when real images arrive

`ProjectCard.tsx` and the `[slug]` hero/gallery use raw `<img>` tags (with `// eslint-disable-next-line @next/next/no-img-element`) because `next.config.mjs` sets `images.unoptimized: true` (mandatory for static export to GH Pages — the `next/image` optimizer needs a Node server). Currently fine — the deliverable `heroImage.src` paths point at placeholders that don't yet exist, so the cream-tinted fallback shows. `loading="lazy"` is already in place on ProjectCard.

**Top recommendation for when real images land (Cycle 7+):**

Add a **`sharp`-based prebuild pipeline** (`scripts/optimize-images.mjs` reading `public/images/source/*.{jpg,png}`, writing WebP + JPEG fallback at 1x/2x widths to `public/images/optimized/`, wired as `"prebuild"` in `package.json`). Then upgrade every `<img>` site (ProjectCard, slug hero, slug gallery, certificates) to ship `srcset="...-800w.webp 800w, ...-1600w.webp 1600w"` + `sizes="(max-width: 768px) 100vw, 800px"`, keep `loading="lazy"` on everything below the fold, and add explicit `width`/`height` attributes to lock layout against CLS. Expected impact at ~5–10 deliverables × ~500 kB raw photo each: cutting a 5 MB unoptimized hero to a properly-sized ~80 kB WebP is the single biggest perf win the next cycle will see. Plan it in **before** real images ship so nothing un-optimized goes live.
