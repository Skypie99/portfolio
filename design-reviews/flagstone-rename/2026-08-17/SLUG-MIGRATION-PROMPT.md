★ THE LAWS (what makes this migration safe rather than merely done):

* REDIRECT OR IT IS A BROKEN LINK. GitHub Pages serves static files: there is no server, no `_redirects`, and `next.config.mjs` `redirects()` does nothing under `output: 'export'`. `/work/accessmap/` is a real URL that exists today, is in the sitemap, and may be linked from anywhere. **If you change the slug without leaving something at the old path, you break it silently.** The mechanism that works here: Next copies `public/` into `out/` verbatim, and `public/` currently holds no HTML, so a hand-written `public/work/accessmap/index.html` lands at `out/work/accessmap/index.html` and is served. Give it `<meta http-equiv="refresh" content="0; url=/work/flagstone/">`, a `<link rel="canonical" href="https://skypistudio.com/work/flagstone/">`, and a real visible sentence with a plain `<a>` for anyone whose refresh is blocked. Same for `/blog/building-accessmap/`. A meta refresh is weaker than a 301 and that is the honest ceiling on this host — say so in the report rather than implying SEO parity.
* IDENTIFIERS THAT ARE NOT OURS DO NOT MOVE. Leave every one of these exactly as-is, and do not "tidy" them: `https://github.com/Skypie99/AccessMap` (the repo kept its name) · `https://accessmap.skypistudio.com` (the live host — the app-side rename pinned it deliberately, along with the `accessmap://` URL scheme and the Supabase redirect URLs) · `/Users/skypie/AccessMap` (a local path in `showcase.manifest.json` and `registry.mjs`) · app storage keys like `accessmap:appearance` and `@accessmap/onboarded_v1` · the `masters/accessmap/...` paths in the manifest, which point at capture sources that do not live in this repo. If you are unsure whether a string is a name or an identifier, it is an identifier — leave it and bank the question.
* `git mv`, NEVER copy-then-delete. 63 files move across two directories; preserve their history.
* TESTS MOVE WITH THE PATHS. The suite pins slugs and asset paths in a lot of places. Two traps, both already hit once on the copy pass: (1) assertions written as **lowercase case-insensitive regexes** (`name: /…accessmap…/i`) do not match a capitalised search-and-replace, and (2) most test data are **self-contained fixtures**, so a wrong rename can leave the suite green while the site is broken. Never treat "tests pass" as proof on its own — prove it against the BUILT output.
* NUMBERS AND CLAIMS ARE NOT YOURS TO TOUCH. The `/work/…` page carries a test-count receipt ("2,971 tests passing · measured 2026-08-16") that was verified by execution. Do not edit, re-derive, or "refresh" it.
